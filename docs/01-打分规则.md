# 打分规则

## 一、候选集怎么来

1. `db.json` 提供三类索引：画师（82 位）、tag（163 个）、模糊词（271 条）
2. `build_pool.py` 用 App API 拉作品：
   - 每个 tag 跑两次检索（`safe` 与 `<tag> R-18`），只收「该 tag 真的在作品 tags 里」的行
   - 每位画师拉 `/v1/user/illusts` 前 N 页
   - 过滤短边 < 600 的图，合并去重
3. 每条记录保留 `bm`（total_bookmarks）、`view`（total_view）、`ai`、`x`（R18）、`tags`

## 二、请求时怎么选

```
候选 = 全池
     ∩ {R18 或 非 R18}          # 按命令类别
     ∩ {命中口语词 tag 子集}     # 有口语词时
     − {本群 7 天内发过的 pid}
     − {不过质量硬门槛的}
排序后取前 TOP_RATIO(30%)，再按 score² 加权随机
```

## 三、三个分项

- `s1 = min(3, 命中偏好 tag 数) / 3` —— **封顶 3 个**，防止靠堆 tag 刷分
- `s2 = 0.5 × percentile^0.75 + 0.5 × abs_quality`
  - `percentile`：在**全池**里的质量分分位（不是候选子集，这点很关键，见下）
  - `abs_quality = 0.75·log10(bm+1)/log10(3001) + 0.25·log10(view+1)/log10(30001)`，封顶 1
- `s3 = 命中偏好画师 ? 1 : 0`
- `score = 1.0·s2 + 0.6·s1 + 0.3·s3`

## 四、为什么要有硬门槛

复盘：某次 R18 出了一张 bm 75 / view 780 的图，用户反馈质量差。查下来：

- 分位是在 **R18 子集内**算的，而 R18 子集本身极弱（bm 的 p10/p50/p90 只有 `4/47/588`，对照非 R18 是 `2/605/14703`）
- bm 75 在 R18 里能排到 p70，于是 `s2` 拿到 0.715
- `s1` 的 0.6 分又把它抬过线

两条修正：**分位改到全池算** + **加绝对门槛**（bm/view 双条件任一满足）。改完同一个池子的通过率从 4206 → 1095，那张图直接被门槛挡掉。

## 五、AI 为什么要单独限流

AI 图在偏好 tag 上命中率高、数量又多，不加限制会挤掉人工图。做法是令牌桶：

```
credit = AI_RATIO × 已发总数 − 已发 AI 数
credit ≥ 1 才允许出 AI
```

再叠一层多级窗口（10/30/50 抽内各不超过 30%），并且要求 AI 的 `s2` 高于人工图中位数 ×1.25。

## 六、7 天去重

`pix_sent(group_id, pid, ts)`：发送前把该群 7 天内的 pid 全部作为 `--exclude` 传给 CLI；发送成功后再写。CLI 侧候选被排除干净时会返回 `empty`，插件据此提示「这个范围内暂时没货」。
